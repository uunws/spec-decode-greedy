# RQ2 — ผลการทดลอง

**คำถามวิจัย:** คุณสมบัติของ *งาน* (workload speculatability) กับ *วิธีดึง draft* (speculation efficiency) ส่งผลต่อความเร็วของ speculative decoding อย่างไร — ทั้งแยกกันและร่วมกัน

---

## 1. ตั้งต้นจากปัญหาอะไร

Speculative decoding ทำงานแบบนี้: มีตัวช่วยเดา (drafter) เสนอ token ล่วงหน้ามาหลายตัว แล้วให้ model ตัวจริง (target) ตรวจทีเดียว ถ้าเดาถูกก็ได้หลาย token ในหนึ่งรอบ ถ้าเดาผิดก็ทิ้ง

ตัวจำลอง (simulator) ที่มีอยู่เดิมวัดความเร็วด้วยสูตร

```
speedup = จำนวน token ที่ต้อง decode ปกติ / จำนวน step ที่ speculate แล้ว
```

**ปัญหาคือสูตรนี้ถือว่า drafter ทำงานฟรี** — ไม่คิดเวลาที่ drafter ใช้ค้นหาเลย ผลก็คือถ้าเราเปลี่ยนวิธีดึง draft ให้เร็วขึ้น 200 เท่า ตัวเลข speedup จะ **ไม่ขยับเลยแม้แต่นิดเดียว** เพราะทั้งสองวิธีเดา token ออกมาเหมือนกันเป๊ะ

แกน "efficiency" ของ RQ2 จึงมองไม่เห็นด้วยเครื่องมือเดิม → ต้องสร้าง cost model ขึ้นมาก่อน

---

## 2. Cost model — สูตรที่ใช้แปลง "นับ token" เป็น "เวลาจริง"

```
speedup  =        L / S
                ─────────────
                1 + ρ + β·B
```

| ตัวแปร | ความหมาย | ได้มาจากไหน |
|---|---|---|
| **L** | ถ้าไม่ speculate ต้อง decode กี่ token | simulator (แม่นเป๊ะ) |
| **S** | speculate แล้วเหลือกี่ step | simulator (แม่นเป๊ะ) |
| **t_d** | drafter ใช้เวลาต่อการเรียกหนึ่งครั้ง | จับเวลาจริงบนเครื่อง |
| **t_v(1)** | target model ตรวจ 1 token นานแค่ไหน | ตั้งเป็นพารามิเตอร์ = 20 ms (ระดับ model 7B) |
| **ρ** (rho) | = t_d / t_v(1) — drafter แพงเทียบกับ target แค่ไหน | คำนวณ |
| **β** (beta) | ตรวจเพิ่มอีก 1 ตำแหน่งแพงขึ้นกี่ % | ตั้งเป็นพารามิเตอร์ = 1% |
| **B** | เสนอกี่ token ต่อ step (draft budget) | ตัวแปรที่กวาด |

**เศษ (L/S)** คือฝั่งงาน — งานที่เดาง่ายจะได้ค่านี้สูง
**ส่วน (1 + ρ + β·B)** คือฝั่งต้นทุน — วิธีดึง draft ที่เร็วจะทำให้ ρ เล็กลง

> **หมายเหตุ:** การทดลองนี้ไม่ต้องรัน model จริงบน GPU เพราะ ρ กับ β ถูกทำเป็น *พารามิเตอร์ที่ประกาศชัดเจน* ไม่ใช่ค่าที่ซ่อนอยู่ ผลลัพธ์จึงรายงานคู่กับค่า ρ ที่วัดได้เสมอ

## 3. ออกแบบเป็นตาราง 4 ช่อง (2×2 factorial)

|  | **on-the-fly** (สแกนใหม่ทุกครั้ง) | **precomputed** (สร้าง index ไว้ก่อน) |
|---|---|---|
| **งานเดายาก** (low-spec) | **A** | **B** |
| **งานเดาง่าย** (high-spec) | **C** | **D** |

- เทียบ **A→B** = ผลของการเปลี่ยนวิธีดึง draft อย่างเดียว
- เทียบ **A→C** = ผลของการเปลี่ยนงานอย่างเดียว
- เทียบ **A→D** = ผลของการเปลี่ยนทั้งสองอย่างพร้อมกัน

## 4. สร้างแกนที่ 1 — ทำยังไงให้งาน "เดายาก" กับ "เดาง่าย" ต่างกันจริง

ลองผิดมา 2 รอบก่อนจะเจอวิธีที่ใช้ได้:

1. แบ่ง request ยาก/ง่ายภายใน dataset เดียวกัน → **ไม่ผ่าน** ต่างกันแค่ 1.17 เท่า น้อยเกินไป
2. เทียบข้าม dataset (Wikipedia vs XSum) → **ไม่ผ่าน** ต่างกัน 1.07 เท่า

**วิธีที่ใช้ได้: เปลี่ยน "ความเกี่ยวข้องของคลังข้อมูล"**

- **pooled** — คลังข้อมูลเป็นบทความอื่น ๆ ที่ไม่เกี่ยวกับคำตอบ
- **self_relevant** — คลังข้อมูลขนาดเท่ากันเป๊ะ แต่มีบทความต้นทางของคำตอบนั้นอยู่ข้างในด้วย

**สำคัญ: จำนวน token ในคลังเท่ากันทุกประการ** ต่างกันแค่ว่ามีเอกสารไหนอยู่ในนั้น

วัดด้วย `oracle_accept_rate` = สัดส่วนตำแหน่งที่ตัวต่อไปซึ่งพบบ่อยที่สุดในคลัง ตรงกับคำตอบจริง (คลัง 200,000 token, 120 requests):

| workload | Q1 | median | Q3 |
|---|---|---|---|
| CNN pooled | 0.0905 | **0.1005** | 0.1206 |
| CNN self_relevant | 0.2412 | **0.2663** | 0.3065 |
| SAMSum pooled | 0.0754 | **0.0905** | 0.1055 |
| SAMSum self_relevant | 0.1256 | **0.1558** | 0.1859 |

CNN ต่างกัน **2.65 เท่า** และช่วง Q1–Q3 ไม่ทับกันเลย → แยกกลุ่มได้ชัด
SAMSum ต่างกัน **1.72 เท่า** ใช้เป็นชุดยืนยันซ้ำ (replication)

*(XSum ต่างกันแค่ 1.15 เท่า จึงไม่ถูกเลือก — เพราะ XSum เป็นงานเขียนใหม่ ไม่ได้คัดลอกจากต้นฉบับ)*

## 5. สร้างแกนที่ 2 — และการควบคุมที่สำคัญที่สุดของงานนี้

สองวิธีดึง draft:
- **on-the-fly** — สแกนคลังทั้งก้อนใหม่ทุกครั้งที่ต้องเดา
- **precomputed** — สร้าง index ไว้ตอนเริ่ม แล้วแค่เปิดดู

**ปัญหาที่ต้องกันไว้:** ถ้าสองวิธีนี้เดา token ออกมา *ไม่เหมือนกัน* ผลที่วัดได้จะปนกันระหว่าง "เร็วกว่า" กับ "เดาเก่งกว่า" → ตีความไม่ได้

**การควบคุม (draft equivalence):** ทุก cell จะตรวจก่อนจับเวลาว่าทั้ง 4 วิธีสร้าง draft ออกมา **เหมือนกันทุก bit** (ตรวจ 244 prompts ต่อ cell) ถ้าไม่เหมือน การทดลองจะหยุดทันที

ระหว่างทางพบ bug จริง 2 จุดที่ทำให้ draft ไม่ตรงกันโดยเงียบ ๆ และแก้ไปแล้ว

**เพราะ draft เหมือนกันเป๊ะ ตัวเลข L/S จึงเท่ากันทุกวิธี** ความต่างที่วัดได้จึงเป็นเรื่องเวลาล้วน ๆ

## 6. เงื่อนไขการทดลอง

- tokenizer: Qwen2.5-0.5B-Instruct (ตัวเดียวทั้งหมด)
- 200 requests ต่อ cell, ยาว 200 token ต่อ request
- ขนาดคลังข้อมูล: 50,000 / 200,000 / 500,000 / 1,000,000 token
- draft budget B: 1, 2, 3, 4, 6, 8
- draft แบบ depth (num_sequences = 1)
- ล็อกไว้ 1 thread, มี warm-up, รายงาน median (ไม่ใช่ mean)

## 7. ผลที่ 1 — สองปุ่มนี้ "คูณกัน" ไม่ใช่ "บวกกัน"

### 📊 [รูปที่ 1 — rq2_1_interaction.png]

รูปนี้มี **2 แผง** — ซ้ายคือคลัง 200,000 token ขวาคือคลัง 1,000,000 token

**แกนนอน:** วิธีดึง draft (on-the-fly → precomputed)
**แกนตั้ง:** speedup (มาตราส่วน log — เลือก log เพราะเรากำลังพูดถึง *อัตราส่วน* ถ้าใช้แกนปกติ เส้นที่เพิ่มขึ้นเท่ากันเชิงอัตราส่วนจะดูถ่างออกจากกันหลอกตา)
**สองเส้นในแต่ละแผง:** งานเดายาก (ล่าง, สีส้ม) กับงานเดาง่าย (บน, สีน้ำเงิน)
**เส้นประแนวนอนที่ 1.00x:** ต่ำกว่านี้คือช้ากว่าไม่ทำ speculative decoding

**สิ่งที่เห็น: เส้นสองเส้นขนานกัน** (ขนานบนแกน log = ขยับขึ้นเป็นอัตราส่วนเท่ากัน)

สังเกตแผงขวา: เส้นสีส้มเริ่มที่ **0.932x คือต่ำกว่าเส้นประ** — งานเดายากที่ใช้ on-the-fly บนคลัง 1M ช้ากว่าการ decode ธรรมดา

### ตัวเลขจริง (คลัง 1,000,000 token, B=4)

| | on-the-fly | precomputed |
|---|---|---|
| งานเดายาก | A = 0.9316 | B = 1.0687 |
| งานเดาง่าย | C = 1.0937 | D = 1.2541 |

คำนวณสามค่า:

```
ผลของ efficiency อย่างเดียว   =  B / A  =  1.0687 / 0.9316  =  1.147 เท่า
ผลของ workload อย่างเดียว     =  C / A  =  1.0937 / 0.9316  =  1.174 เท่า
ผลของทั้งสองพร้อมกัน (joint)  =  D / A  =  1.2541 / 0.9316  =  1.346 เท่า
```

ถ้าสองปุ่มไม่ยุ่งกัน ผลรวมควรเท่ากับผลคูณ:

```
1.147 × 1.174  =  1.347     ← ค่าที่ควรได้
                   1.346     ← ค่าที่วัดได้จริง
```

**ต่างกัน 0.1%**

### เป็นแบบนี้ทุกช่อง ทั้งสอง dataset

| dataset | คลัง | efficiency | workload | joint (วัดได้) | joint (ที่ควรได้) | อัตราส่วน |
|---|---|---|---|---|---|---|
| CNN | 50,000 | 1.008× | 1.074× | 1.082× | 1.082× | 1.0000 |
| CNN | 200,000 | 1.031× | 1.190× | 1.227× | 1.226× | 1.0002 |
| CNN | 500,000 | 1.076× | 1.185× | 1.275× | 1.275× | 0.9997 |
| CNN | 1,000,000 | 1.147× | 1.174× | 1.346× | 1.347× | 0.9995 |
| SAMSum | 50,000 | 1.008× | 1.118× | 1.127× | 1.127× | 1.0001 |
| SAMSum | 200,000 | 1.031× | 1.113× | 1.147× | 1.148× | 0.9997 |
| SAMSum | 500,000 | 1.076× | 1.105× | 1.189× | 1.189× | 0.9999 |
| SAMSum | 1,000,000 | 1.053× | 1.103× | 1.161× | 1.161× | 1.0002 |

**คลาดเคลื่อนไม่เกิน 0.05% ทุกช่อง**

### ตีความ

ค่านี้ไม่ได้ "มหัศจรรย์" — cost model **ทำนายไว้ล่วงหน้าแล้ว** ว่าต้องเป็นแบบนี้ เพราะ workload อยู่ที่เศษ ส่วน efficiency อยู่ที่ส่วน หารกันแล้วจึงคูณกันโดยธรรมชาติ

**คุณค่าของผลนี้คือมันเป็นการ *ทดสอบ* สมมติฐานที่พิสูจน์ผิดได้** ถ้าอัตราส่วนออกมาไม่ใช่ 1.000 จะแปลว่างานที่เดาง่ายไปทำให้ drafter ทำงานหนักขึ้น/เบาลงด้วย (คือ workload ไปขยับ ρ) — เราตรวจแล้วว่า **ไม่เกิด**

**ความหมายเชิงปฏิบัติ:** ปรับปรุงสองด้านนี้แยกกันได้ ไม่ต้องกลัวว่าทำอย่างหนึ่งแล้วอีกอย่างจะไร้ผล

## 8. ผลที่ 2 — ต้นทุนการค้นหาโตตามขนาดคลัง แต่โตคนละแบบ

### 📊 [รูปที่ 2 — rq2_2_retrieval_cost.png]

**แกนนอน:** ขนาดคลังข้อมูล 50K → 1M (มาตราส่วน log)
**แกนตั้ง:** เวลา median ที่ drafter ใช้ต่อการเรียกหนึ่งครั้ง หน่วยไมโครวินาที (มาตราส่วน log)
**สี่เส้น:** เราวัดทั้ง 4 การ implement — on-the-fly 2 แบบ (tensor scan, python scan) และ precomputed 2 แบบ (tensor index, dict index)

**เส้นบนสองเส้น (สแกน) ลาดขึ้น เส้นล่างสองเส้น (index) แบนราบ** — นี่คือภาพรวมทั้งหมดของแกน efficiency

*(การทดลองหลักใช้คู่ tensor scan ↔ tensor index เพราะเป็นคู่ที่โค้ดส่วนเลือก candidate เหมือนกันตัวต่อตัว อีกสองเส้นเป็นตัวยืนยันว่าแนวโน้มไม่ได้ขึ้นกับ implementation)*

### ตัวเลขจริง (CNN, เวลา median ต่อการเรียก 1 ครั้ง)

| ขนาดคลัง | on-the-fly | precomputed | เร็วกว่ากี่เท่า |
|---|---|---|---|
| 50,000 | 170,938 ns | 11,166 ns | 15× |
| 200,000 | 652,125 ns | 11,625 ns | 56× |
| 500,000 | 1,594,791 ns | 12,042 ns | 132× |
| 1,000,000 | 3,067,625 ns | 14,875 ns | **206×** |

**on-the-fly โตแบบเชิงเส้นตามขนาดคลัง** (คลังโต 20 เท่า → ช้าลง 18 เท่า)
**precomputed แทบไม่โตเลย** (คลังโต 20 เท่า → ช้าลงแค่ 1.3 เท่า)

แปลงเป็น ρ ที่คลัง 1M:
```
on-the-fly:   ρ = 0.152    ← drafter กินเวลา 15% ของ target model
precomputed:  ρ = 0.00073  ← แทบไม่กินเลย
```

### สิ่งที่ต้องแลก

| | on-the-fly | precomputed |
|---|---|---|
| เวลาสร้าง index (คลัง 1M) | 28 ms | 362 ms |
| หน่วยความจำ | 8 MB | 76.6 MB |

precomputed ต้องจ่ายค่าสร้างก่อน แต่ **จ่ายครั้งเดียว** — ถ้ามี 100 requests ใช้ index เดียวกัน ค่านี้เฉลี่ยแล้วแทบหายไป (จาก reuse curve: R=1 ได้ 1.2534 / R=100 ได้ 1.2541)

> **หมายเหตุการวัด:** เส้น python scan ลดลงจาก 500K → 1M ซึ่งขัดกับที่ควรเป็น สาเหตุคือ python scan ช้ามากจนชนเพดานเวลาที่ตั้งไว้ต่อการวัด ทำให้ที่ 1M เก็บตัวอย่างได้น้อยกว่าและได้ชุด prompt ที่ต่างออกไป **ตัวเลขนี้ไม่ถูกใช้ในการทดลองหลัก** (การทดลองหลักใช้ tensor scan ↔ tensor index)

## 9. ผลที่ 3 — จุดที่ speculative decoding เริ่ม "ขาดทุน"

### 📊 [รูปที่ 3 — rq2_3_speedup_by_datastore.png]

**แกนนอน:** ขนาดคลังข้อมูล 50K → 1M
**แกนตั้ง:** speedup ที่โมเดลคำนวณได้
**สี่เส้น = ตาราง 4 ช่องพอดี:** น้ำเงิน = D (ง่าย+precomputed), ส้ม = C (ง่าย+on-the-fly), เขียว = B (ยาก+precomputed), เหลือง = A (ยาก+on-the-fly)
**เส้นประแนวนอนที่ 1.00:** เส้นคุ้มทุน — ต่ำกว่านี้คือ "ช้ากว่าไม่ทำ speculative decoding เลย"

**สิ่งที่เห็น: เส้น precomputed (น้ำเงิน, เขียว) ไต่ขึ้นเรื่อย ๆ ส่วนเส้น on-the-fly (ส้ม, เหลือง) ขึ้นแล้วหักหัวลง**

### ตัวเลขจริง (CNN, B=4)

| ขนาดคลัง | A (ยาก+fly) | B (ยาก+pre) | C (ง่าย+fly) | D (ง่าย+pre) |
|---|---|---|---|---|
| 50,000 | 1.0291 | 1.0371 | 1.1050 | 1.1135 |
| 200,000 | 1.0179 | 1.0491 | 1.2114 | 1.2486 |
| 500,000 | **0.9817** | 1.0568 | 1.1631 | 1.2515 |
| 1,000,000 | **0.9316** | 1.0687 | 1.0937 | 1.2541 |

**cell A ตกต่ำกว่า 1.0 ตั้งแต่คลัง 500,000 token**

### ตีความ — นี่คือผลที่สำคัญที่สุดของ RQ2

คลังที่ใหญ่ขึ้นให้ **ประโยชน์** เพราะเจอ match มากขึ้น แต่ก็มี **ต้นทุน** เพราะสแกนนานขึ้น

- ถ้าใช้ **on-the-fly** ต้นทุนโตเร็วกว่าประโยชน์ → พอคลังใหญ่ระดับหนึ่ง **ยิ่งเพิ่มข้อมูลยิ่งช้าลง** และสุดท้ายแย่กว่าไม่ทำเลย
- ถ้าใช้ **precomputed** ต้นทุนแทบไม่โต → คลังยิ่งใหญ่ยิ่งดี (1.0371 → 1.0687 และ 1.1135 → 1.2541)

**บทสรุป:** "คลังใหญ่ขึ้นดีกว่า" เป็นจริง **ก็ต่อเมื่อ** ใช้วิธีดึงที่เหมาะสม ถ้าเลือกวิธีผิด การเพิ่มข้อมูลกลายเป็นการทำร้ายตัวเอง — และตัวเลข speedup แบบนับ token เดิม **มองไม่เห็นเรื่องนี้เลย** เพราะ A กับ B ได้ L/S เท่ากันเป๊ะ

## 12. ข้อจำกัดที่ต้องระบุใน paper

1. **ρ ข้าม hardware** — เวลา drafter วัดบน CPU ส่วน t_v(1) เป็นค่าสมมติของ GPU การเทียบข้าม device นี้ทำให้ผลของ on-the-fly ดู **แย่กว่าความจริง** (pessimistic) จึงรายงาน ρ ควบคู่เสมอ และทำ ρ เป็นแกนกราฟ
2. **ยังไม่มี validation กับ model จริง** — ควรรัน end-to-end 1 workload เทียบ measured vs modeled ให้ต่างไม่เกิน 20%
3. **ใช้ ground truth แทน target model** — greedy decoding จริงให้ข้อความที่ซ้ำมากกว่า reference text ซึ่ง n-gram drafter น่าจะ match ได้ง่ายกว่า ดังนั้น L/S ที่รายงานน่าจะเป็น **ขอบล่าง** ของของจริง
4. **ทดลองเฉพาะ depth drafting** (num_sequences=1) — การเทียบ depth vs width เก็บไว้เป็นภาคผนวก
