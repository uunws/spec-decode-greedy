RQ3 History Scoping

การจำกัดขอบเขต history ยกระดับ workload speculatability ได้ไหม โดยไม่เปลี่ยนอัลกอริทึม speculative decoding

สิ่งที่วัด speculatability ตามที่ RQ1 นิยาม คือ historical support คู่กับ prefix branching entropy ทั้งสองตัววัดจากข้อความล้วน ไม่ต้องรัน drafter และไม่มีตัวไหนเกี่ยวกับความเร็ว

สิ่งที่เปลี่ยน ขอบเขตของ history ที่เอาไป build datastore ทั้งหมด 3 ระดับ โดย drafter ใช้คลาสเดียวพารามิเตอร์ชุดเดียวตลอด

คำถามที่ตอบ พอเปลี่ยน scope แล้ว workload ขยับไปทาง quadrant ไหนบนระนาบสองแกนนี้

1. วิธีวัด

สองแกน

  • History คือ mean_support จำนวนครั้งที่ prefix ปรากฏใน datastore สูงคือดี
  • Structure คือ 1 - normalized_branch_entropy ยิ่งสูงยิ่งแปลว่า prefix ชี้ไปยัง token ถัดไปแบบเดียว ไม่แตกหลายทาง สูงคือดี
  • coverage สัดส่วนตำแหน่งใน target ที่หา match เจอ ต้องรายงานคู่กับ support เสมอ เพราะ support เฉลี่ยเฉพาะตำแหน่งที่หาเจอ ตำแหน่งที่หาไม่เจอถูกตัดทิ้งก่อนหาค่าเฉลี่ย

speculatability สูงสุดอยู่มุมขวาบน ต่ำสุดอยู่มุมซ้ายล่าง

scope 3 ระดับ

group    เฉพาะกลุ่มเดียวกับ request     กลาง

history หนึ่งชิ้นคือ prompt บวกคำตอบของ request ก่อนหน้า เพราะระบบจริงเก็บทั้งสองอย่าง

คู่เทียบขนาดเท่ากัน

การแคบ scope เปลี่ยนสองอย่างพร้อมกัน คือ history เกี่ยวข้องขึ้น แต่ corpus เล็กลงด้วย ถ้าวัดแค่ scope sweep อย่างเดียว support ที่ลดลงอธิบายได้ด้วยเหตุผลง่าย ๆ ว่าข้อความน้อยลง ไม่ได้พิสูจน์อะไรเรื่องความเกี่ยวข้อง

ทุก scope จึงจับคู่กับ datastore ที่ มีจำนวน token เท่ากันเป๊ะแต่สุ่มเนื้อหามา ต่างกันแค่ว่า token ไหนอยู่ข้างใน สิ่งที่เหลือให้อธิบายจึงมีแค่ความเกี่ยวข้องอย่างเดียว

สิ่งที่ตรวจก่อนบันทึกผลทุกครั้ง

  • ไม่มีเอกสารจากอนาคตหลุดเข้า datastore
  • คู่เทียบมีขนาดต่างจากของจริงไม่เกิน 1 เปอร์เซ็นต์
  • datastore หนึ่งชุดต้องผูกกับ scope เดียวเท่านั้น

5. ข้อสรุป

  1. ความแคบของ scope ไม่ใช่ตัวแปรที่ยกระดับ speculatability มันย้าย workload ไปมุมขวาล่าง คือแลก support ทิ้งเพื่อซื้อ structure ทุก dataset
  2. ความเกี่ยวข้องของ history คือตัวแปรที่ยกระดับได้จริง เพราะเมื่อตรึงขนาด corpus ไว้เท่ากัน มันดัน structure และ coverage ขึ้นทุกคู่
  3. เพราะฉะนั้น ถ้าจะเลื่อนตำแหน่ง workload บน matrix ต้องเลื่อนด้วยความเกี่ยวข้อง ไม่ใช่ด้วยการตัด history ให้เล็กลง

ทั้งสามข้อสรุปได้มาโดยไม่แตะอัลกอริทึม speculative decoding เลย เปลี่ยนแค่ว่า token ชุดไหนถูกใส่เข้าไปใน datastore

6. ข้อจำกัด

  • รันที่ n-gram order เท่ากับ 3 อย่างเดียว ยังไม่ได้กวาดค่าอื่น
  • คู่เทียบสุ่มใช้ seed เดียว จึงยังไม่มี error bar
  • ข้อที่ว่า support ลดใน 5 คู่เพราะ coverage เพิ่มนั้น ยังอธิบายด้วยเหตุผล ยังไม่ได้พิสูจน์ตรง ๆ วิธีพิสูจน์คือเทียบ support เฉพาะตำแหน่งที่ทั้งสองฝั่งหาเจอเหมือนกัน
  • history ถูกวางไว้ทั้งหมดก่อนเริ่มให้บริการ request จึงยังไม่ได้ทดสอบกรณีที่ history โตขึ้นระหว่างทาง
