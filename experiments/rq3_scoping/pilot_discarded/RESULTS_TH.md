# RQ3 — ผลการทดลอง: History Scoping

**คำถามวิจัย:** การจำกัดขอบเขตของประวัติ (history scoping) ช่วยยกระดับ workload speculatability ได้ไหม โดยไม่แตะ algorithm ของ speculative decoding

**สมมติฐานตั้งต้น:** scope แคบลง → เกี่ยวข้องมากขึ้น → เดาเก่งขึ้น ทั้งที่ corpus เล็กลง

**คำตอบสั้น:** ได้ แต่กลไกไม่ใช่ "แคบแล้วดี" อย่างที่คิด — มันมีสองระบอบที่ไม่ต่อเนื่องกัน และมีขอบเขตที่ชัดเจนว่าเก็บประวัติไปถึงไหนแล้วหยุด

---

## 1. ตั้งต้นจากอะไร

RQ2 ตอบว่า speculatability กับ efficiency ส่งผลต่อ speedup อย่างไร แต่**รับ speculatability มาเป็นของที่มีอยู่แล้ว**

RQ3 ถามต่อว่า **เอา workload เดิม แล้วดัน speculatability ขึ้นเองได้ไหม โดยเปลี่ยนแค่ว่าจะเก็บประวัติส่วนไหนไว้ในคลัง**

`IndexedTensorNGramDrafter` รับ `NGramIndex` สำเร็จรูปอยู่แล้ว เราจึงแค่ป้อน index คนละก้อนให้ drafter คลาสเดิม — **ไม่มีบรรทัดไหนของ algorithm เปลี่ยน** ซึ่งเป็นเงื่อนไขที่ RQ3 กำหนดไว้

---

## 2. ตัววัด speculatability

ใช้ตัวที่ RQ1 กำหนดไว้:

```
historical support        suffix ที่ match ได้ โผล่ในคลังกี่ครั้ง          (สูง = ดี)
prefix branching entropy  พอ match ได้ ตัวถัดไปแตกกี่ทาง (bits)          (ต่ำ = ดี)
coverage                  สัดส่วนตำแหน่งที่หา match ได้เลย

score = coverage × (1 − normalized entropy)
```

สองตัวชี้คนละทาง (support สูงดี / entropy สูงแย่) score จึงกลับด้าน entropy ก่อนคูณ

> **ตรวจแล้วว่าใช้ได้จริง** — score correlate กับ speedup ที่วัดได้ **+0.980** (ดูหัวข้อ 10 ซึ่งระบุด้วยว่าใช้เดี่ยว ๆ ไม่ได้ และพลาดตรงไหน)

## 3. ปัญหาที่ต้องแก้ก่อน: จะเอา "กลุ่ม" มาจากไหน

RQ3 ต้องมีสถานการณ์ที่ **หลาย request ใช้ประวัติร่วมกัน** แต่**ไม่มี dataset ไหนในเรปมี user id หรือ session id เลย**

| ทางเลือก | กลุ่ม | ปัญหา |
|---|---|---|
| SQuAD `title` | ของจริง 442 หัวข้อ มัธยฐาน 169 คำถาม/หัวข้อ | คำตอบยาว 2.4 คำ (~3 token) → speedup กระโดดเป็นขั้น วัดไม่ได้ |
| Wikipedia แบ่งบทความเป็นช่วง | causality ธรรมชาติ | บทความหนึ่งได้ ~4 ช่วง → R≈4 อ่อนเกินไป |
| **ใช้ dataset เป็นกลุ่ม** | ✅ ของจริง ไม่ต้องสังเคราะห์ | ต้องมีหลาย domain (ซึ่งต้องการอยู่แล้ว) |

**ทางที่เลือก: dataset คือกลุ่ม** — request จาก CNN เห็นแค่ประวัติข่าว CNN, request จาก arXiv เห็นแค่ประวัติเปเปอร์

**การมีหลาย dataset จึงไม่ใช่แค่ replication แต่เป็นสิ่งที่ทำให้แกนกลุ่มมีอยู่ได้**

## 4. ออกแบบการทดลอง

### ประวัติทั้งหมด 2,547 เอกสาร = 1,001,722 token

| domain | dataset | เอกสาร | เฉลี่ย/เอกสาร |
|---|---|---|---|
| ข่าว extractive | CNN/DailyMail | 282 | 711 token |
| ข่าว abstractive | XSum | 458 | 436 token |
| บทสนทนา | SAMSum | 1,414 | 141 token |
| วิทยาศาสตร์ | arXiv | 197 | 1,019 token |
| สารานุกรม | Wikipedia | 196 | 1,020 token |

ทุก domain มีประวัติ ~200,000 token เท่ากัน

### 4 ระดับของ scope (รัน 7 cell)

```
request-local   คลัง = เอกสารต้นทางของ request นี้เท่านั้น        557 token
narrow(N)       คลัง = ประวัติ N เอกสารล่าสุดของ domain เดียวกัน   N = 1, 5, 10, 50
domain          คลัง = ประวัติทั้งหมดของ domain เดียวกัน           200,344 token
global          คลัง = ประวัติทั้งหมดทุก domain                    1,001,722 token
```

`narrow` กวาดหลายค่าเพื่อให้ได้**เส้นโค้ง** ไม่ใช่แค่จุดเดียว — จะได้รู้ว่ามี sweet spot ตรงกลางไหม

> **`request-local` ไม่ใช่จุดหนึ่งบนแกน "ความกว้างของประวัติ"** — คลังของมันคือ *prompt* ไม่ใช่ประวัติที่เก็บไว้ ในกราฟจึงวาดเป็น**เส้นอ้างอิงแนวนอน** ไม่ใช่จุดบนเส้นโค้ง

### แบ่งครึ่งเพื่อกัน leakage

```
ประวัติ (เสิร์ฟไปแล้ว)  →  เข้าคลังได้
request ที่เอามาวัดผล   →  มาทีหลังเสมอ ไม่เคยเข้าคลัง
```

### เงื่อนไขที่คงที่ทุก scope

tokenizer Qwen2.5-0.5B-Instruct · 40 request/domain = **200 request** × 200 token (ชุดเดียวกันเป๊ะทุก scope) · draft budget B=4 · depth drafting · n=3 · 1 thread · ทิ้ง warm-up · รายงาน median + p95

**เปลี่ยนอย่างเดียวคือ "คลังมีอะไรอยู่ข้างใน"**

## 5. การควบคุม 4 ชั้น

นี่คือ 4 วิธีที่การทดลองนี้จะโกหกเราได้ และวิธีปิด

**ชั้นที่ 1 — คลังต้องไม่มีอนาคต**
ถ้าคลังมีเอกสารของ request ที่ยังไม่ถึงคิว จะเดาถูกเยอะแบบปลอม ๆ
โค้ดที่เลือกเอกสารรับรายการที่**กรองแล้ว**เท่านั้น (`visible_history` ตัด `order ≥ request.order` ทิ้ง) → เลือกของอนาคตไม่ได้เพราะไม่รู้ว่ามีอยู่ และ `assert_causal()` ตรวจซ้ำก่อนวัดผลทุก cell

**ชั้นที่ 2 — คลังชื่อเดียวกันต้องเป็นคลังเดียวกัน**
เราสร้าง index ครั้งเดียวให้ 40 request ใช้ร่วมกัน ถ้า 40 คนนั้นควรได้คลังต่างกัน 39 คนจะได้คลังของคนแรก

> **นี่คือ bug จริงที่เจอระหว่างพัฒนา** เวอร์ชันแรกใส่เอกสารต้นทางของ request ลงในคลังที่แชร์กัน ทำให้ 39 จาก 40 request ถูกวัดด้วยเอกสารของคนอื่น **ผลผิดทั้งหมดและดู "น่าสนใจ" มาก** (control ชนะ treatment)
> แก้โดยแยกให้ชัดว่า **เอกสารต้นทาง = prompt ไม่ใช่ประวัติ** และเพิ่ม `assert_key_determines_tokens()` ตรวจทุก cell ว่าชื่อคลังเดียวกันต้องได้ token ชุดเดียวกันเสมอ

**ชั้นที่ 3 — แยก "เกี่ยวข้อง" ออกจาก "เล็ก"**
scope แคบลงมี 2 อย่างเปลี่ยนพร้อมกัน (เล็กลง + เกี่ยวข้องขึ้น) และ RQ2 แสดงแล้วว่าขนาด corpus เปลี่ยนผลด้วยตัวมันเอง
ทุก treatment จึงมีฝาแฝด **ขนาดเท่ากันเป๊ะระดับ token แต่สุ่มเอกสารจากทั้ง pool** ผลต่างคือ relevance ล้วน ๆ

**ชั้นที่ 4 — control ต้องสร้าง index เท่ากัน**
ถ้า control สุ่มคลังใหม่ทุก request มันจะสร้าง index 200 ก้อนเทียบกับ treatment 5 ก้อน แล้วคอลัมน์ "รวมต้นทุน build" จะวัดว่าใครสร้าง index ถี่กว่าแทนที่จะวัด relevance
control จึงสืบโครงสร้างการแบ่งกลุ่มจาก treatment → สร้าง index เท่ากัน มี R เท่ากัน

```
ชั้น 1-2  กันไม่ให้ตัวเลขผิด
ชั้น 3-4  กันไม่ให้ตีความผิด
```

## 6. ผลที่ 1 — เส้นโค้งความกว้างของประวัติ

### 📊 [รูปที่ 1 — rq3_1_sweet_spot.png]

**แกนนอน:** จำนวน token ในคลังต่อ request (log) เรียงจากแคบไปกว้าง
**แกนตั้ง:** speedup ที่โมเดลคำนวณได้
**เส้นน้ำเงิน:** ประวัติที่เก็บไว้ (narrow → domain → global)
**เส้นประเขียวแนวนอน:** request-local (prompt ล้วน 557 token)
**เส้นประเทาที่ 1.00:** เส้นคุ้มทุน

> วาดเส้นเดียว ไม่แยก "รวม/ไม่รวมต้นทุนสร้าง index" เพราะ**สองอันต่างกันไม่เกิน 0.04%** จนทับกันสนิท — scope ที่กว้างที่สุดใช้ 16 step-equivalent ในการสร้าง index เทียบกับงานทั้งหมด 36,188 step (รายละเอียดหัวข้อ 11)

### 📊 [รูปที่ 4 — rq3_4_tradeoff.png]

**สามแผงใช้แกนนอนร่วมกัน** (ไม่ใช้แกนตั้งสองอันในกราฟเดียว)
บน = historical support (log) · กลาง = normalized branching entropy · ล่าง = score รวม

### ตัวเลข

| scope | คลัง (token) | support | entropy (bits) | norm-ent | coverage | **score** | L/S | speedup |
|---|---|---|---|---|---|---|---|---|
| request-local | 557 | 6.2 | 1.2367 | **0.5404** | 0.4584 | 0.2107 | 1.091 | **1.0491** |
| narrow(1) | 690 | 9.3 | 1.5677 | 0.5802 | 0.3063 | **0.1286** | 1.016 | **0.9768** |
| narrow(5) | 3,137 | 27.3 | 2.2280 | 0.7170 | 0.5201 | 0.1472 | 1.034 | 0.9945 |
| narrow(10) | 6,384 | 46.4 | 2.5016 | 0.7102 | 0.5907 | 0.1711 | 1.046 | 1.0057 |
| narrow(50) | 32,291 | 131.7 | 2.8624 | 0.7240 | 0.7725 | 0.2132 | 1.072 | 1.0304 |
| domain | 200,344 | 424.4 | 3.1481 | 0.7316 | 0.9223 | **0.2476** | 1.101 | **1.0583** |
| global | 1,001,722 | 1,185.7 | 3.5647 | 0.7563 | 0.9783 | 0.2384 | 1.100 | 1.0574 |

### อ่านยังไง

**ภายในแกน "ความกว้างของประวัติ" กว้างกว่าดีกว่าเสมอ จนถึงขอบเขต domain แล้วเริ่มลดลง**

```
narrow(1) 0.1286  ──►  narrow(50) 0.2132  ──►  domain 0.2476  ──►  global 0.2384
   690 tok                32,291 tok             200,344 tok        1,001,722 tok
   แย่ที่สุด                                        ดีที่สุด            เริ่มถอย
```

**ไม่มี sweet spot ตรงกลาง** — สมมติฐาน "แคบลงแล้วดีขึ้น" **ไม่จริงสำหรับประวัติ**

**narrow(1) และ narrow(5) ให้ speedup ต่ำกว่า 1.0** (0.9768 และ 0.9945) แปลว่า **เก็บประวัติไว้นิดหน่อยแย่กว่าไม่เก็บเลย** — support ไม่พอที่จะเดาถูก แต่เสียเวลาค้นหาไปแล้ว

### สองตัวตั้งต้นชี้คนละทางอย่างชัดเจน

```
support   6.2 → 1,185.7      โต 190 เท่า      (ดีขึ้น)
norm-ent  0.5404 → 0.7563    โต 0.22          (แย่ลง)
```

คลังใหญ่ขึ้นให้หลักฐานมากขึ้นก็จริง แต่ก็ทำให้ตัวเลือกแตกทางเยอะขึ้นด้วย **นี่คือเหตุผลที่ต้องใช้เป็นคู่ ไม่ใช่ตัวเดียว**

## 7. ผลที่ 2 — prompt ให้ผลเท่าประวัติที่ใหญ่กว่า 58 เท่า

```
request-local      557 token   score 0.2107   speedup 1.0491
narrow(50)      32,291 token   score 0.2132   speedup 1.0304
                       ↑
                 ใหญ่กว่า 58 เท่า แต่ score เท่ากัน และช้ากว่า
```

**score เกือบเท่ากันเป๊ะ (0.2107 vs 0.2132) ทั้งที่ใช้ข้อมูลต่างกัน 58 เท่า**

และ request-local (1.0491) แพ้เฉพาะ domain (1.0583) กับ global (1.0574) ซึ่งใหญ่กว่า **360 เท่าและ 1,800 เท่า**

**ทำไม prompt ถึงมีประสิทธิภาพต่อ token สูงขนาดนั้น** — ดูที่ entropy: request-local มี norm-ent **0.5404 ต่ำที่สุดในทุก scope** แปลว่าเมื่อ match ได้ ตัวเลือกถัดไปแทบไม่แตกทางเลย ตรงข้ามกับคลังใหญ่ที่ match ได้บ่อยแต่แตกทางเยอะ

```
                coverage   norm-ent   → score
request-local     0.4584    0.5404      0.2107    หาเจอน้อย แต่เจอแล้วชัด
domain            0.9223    0.7316      0.2476    หาเจอเกือบหมด แต่กำกวมกว่า
```

## 8. ผลที่ 3 — ทิ้งข้อมูล 80% แล้วดีขึ้นด้วยซ้ำ

**domain (200,344 token) เทียบกับ global (1,001,722 token)**

| | support | norm-ent | coverage | score | L/S | speedup | build | หน่วยความจำ |
|---|---|---|---|---|---|---|---|---|
| domain | 424.4 | **0.7316** | 0.9223 | **0.2476** | **1.101** | **1.0583** | 58.9 ms | 21.4 MB |
| global | 1,185.7 | 0.7563 | 0.9783 | 0.2384 | 1.100 | 1.0574 | 305.6 ms | 92.4 MB |

**global มี support มากกว่า 2.8 เท่าและ coverage สูงกว่า แต่ score ต่ำกว่า** เพราะ entropy สูงขึ้น — ข้อมูลข้าม domain เพิ่มทางเลือกที่ผิดเข้ามามากกว่าที่ช่วย

domain ใช้ข้อมูลน้อยกว่า 5 เท่า สร้าง index เร็วกว่า 5.2 เท่า กินแรมน้อยกว่า 4.3 เท่า **และได้ผลดีกว่าเล็กน้อย**

| domain | score (domain) | score (global) | L/S (domain) | L/S (global) |
|---|---|---|---|---|
| arXiv | **0.2682** | 0.2530 | **1.1622** | 1.1595 |
| CNN | 0.2205 | **0.2371** | 1.0796 | **1.0806** |

**4 ใน 5 domain ดีขึ้นเมื่อจำกัดเป็น domain เดียว**

**ข้อสรุปเชิงปฏิบัติ:** การเก็บประวัติข้าม domain ไม่ให้ประโยชน์ แต่จ่ายค่าหน่วยความจำและเวลาสร้าง index เต็ม ๆ

## 9. ผลที่ 4 — แยก relevance ออกจากขนาดด้วย control

### 📊 [รูปที่ 3 — rq3_3_relevance_vs_size.png]

**แกนนอน:** scope · **แกนตั้ง:** ซ้าย = score, ขวา = speedup
**สองแท่งต่อคู่:** น้ำเงิน = scope จริง / ส้ม = ขนาดเท่ากันแต่สุ่มเอกสาร
**ตัวเลขบนแท่ง:** อัตราส่วน treatment ÷ control

### ตัวเลขรวม

| scope | support (จริง / สุ่ม) | norm-ent (จริง / สุ่ม) | score (จริง / สุ่ม) | อัตราส่วน | speedup (จริง / สุ่ม) |
|---|---|---|---|---|---|
| request-local | 6.2 / 6.3 | **0.5404 / 0.6418** | 0.2107 / 0.1106 | **1.90×** | 1.0491 / 0.9725 |
| narrow(10) | 46.4 / 36.8 | 0.7102 / 0.7380 | 0.1711 / 0.1441 | 1.19× | 1.0057 / 0.9890 |
| domain | 424.4 / 412.4 | 0.7316 / 0.7425 | 0.2476 / 0.2353 | **1.05×** | 1.0583 / 1.0309 |

**คลังขนาดเท่ากันเป๊ะระดับ token** ความต่างทั้งหมดคือ relevance

**สังเกต request-local:** support แทบเท่ากัน (6.2 vs 6.3) — ความได้เปรียบมาจาก **entropy ล้วน ๆ** (0.5404 vs 0.6418) prompt ไม่ได้ให้ข้อมูล*มากกว่า* แต่ให้ข้อมูลที่*กำกวมน้อยกว่า*

### ⚠️ จุดที่ต้องรายงานตามจริง

**`domain` ชนะการสุ่มแค่ 1.05× ตาม score** ทั้งที่ speedup ที่วัดได้ต่างกัน 1.027× อย่างชัดเจน

แยกราย domain:

| domain | score (จริง) | score (สุ่ม) | อัตราส่วน |
|---|---|---|---|
| Wikipedia | 0.2366 | 0.2122 | 1.12× |
| SAMSum | 0.2715 | 0.2462 | 1.10× |
| XSum | 0.2424 | 0.2355 | 1.03× |
| arXiv | 0.2682 | 0.2639 | 1.02× |
| CNN | 0.2205 | 0.2209 | **1.00×** |

**ที่คลังใหญ่ (200k token) score แยกความต่างแทบไม่ออก** — เป็นข้อจำกัดด้านความไวของตัววัด ไม่ใช่ว่า domain scoping ไม่มีผล เพราะ speedup ที่วัดตรง ๆ บอกว่ามีผล

**narrow(10) ราย domain ก็ไม่สม่ำเสมอ:** SAMSum 2.05× / arXiv 1.34× / CNN 1.08× / XSum 1.04× / **Wikipedia 0.85×** (แพ้การสุ่ม)

เอกสารที่อยู่ติดกันในลำดับมีเนื้อหาซ้ำกันสูง (วัดได้: distinct 2-gram ต่อ token ของ arXiv narrow window = 0.54 เทียบกับสุ่ม 0.71) **recency จึงไม่ใช่ heuristic ที่ดีสำหรับ scoping** ซึ่งขัดกับสิ่งที่ระบบส่วนใหญ่ทำ

## 10. ตรวจสอบตัววัด

### 📊 [รูปที่ 2 — rq3_2_movement.png]

**แกนนอน:** score · **แกนตั้ง:** speedup · **5 เส้น:** 5 domain แต่ละจุดคือ scope หนึ่ง
ถ้า scoping ทำงานผ่าน speculatability อย่างเดียว ทุกจุดของ domain หนึ่งต้องเรียงอยู่บนเส้นโค้งขาขึ้นเส้นเดียว

### score ทำนาย speedup ได้ดี

**correlation กับ speedup ที่วัดได้**

| ตัววัด | รวมทุก domain | เฉลี่ยราย domain |
|---|---|---|
| **score (coverage × (1−nEnt))** | **+0.980** | **+0.947** |
| coverage เดี่ยว | +0.767 | — |
| mean support เดี่ยว | +0.612 | +0.553 |
| normalized entropy เดี่ยว | +0.254 | **+0.084** |

### ⚠️ ข้อควรระวัง 3 ข้อ

**1. ใช้เดี่ยว ๆ ไม่ได้**
normalized entropy อย่างเดียว correlate กับ speedup แค่ **+0.084** และ**ติดลบใน 3 จาก 5 domain** (arXiv −0.116, CNN −0.156, Wikipedia −0.483) ต้องใช้เป็นคู่เท่านั้น

**2. entropy ดิบเกือบเป็นตัววัดขนาดคลัง**

correlation กับ log(ขนาดคลัง):

```
mean_branch_entropy   +0.970   ← แทบเป็นฟังก์ชันของขนาดคลังล้วน ๆ
coverage              +0.973
mean_support          +0.864
score                 +0.746
```

คลังใหญ่ → แตกทางเยอะ → entropy สูง โดยไม่เกี่ยวกับว่างานเดาง่ายหรือยาก
**นี่คือเหตุผลที่ต้องมี size-matched control เสมอ** ไม่งั้นจะรายงาน "ขนาดคลัง" โดยเรียกมันว่า "speculatability"

**3. จัดอันดับผิด 1 จุด**

```
score จัดอันดับ    domain > global > narrow(50) > request-local > narrow(10) > narrow(5) > narrow(1)
speedup จริง       domain > global > request-local > narrow(50) > narrow(10) > narrow(5) > narrow(1)
                                     └──────── สลับกัน ────────┘
```

score จัด request-local (557 token) ต่ำกว่า narrow(50) (32,291 token) ทั้งที่ของจริงเร็วกว่า
สาเหตุ: สูตรคูณด้วย `coverage` ซึ่ง request-local ต่ำ (0.4584) เพราะคลังเล็ก — **สูตรลงโทษกรณี "เจอน้อยแต่แม่น"** ซึ่งเป็นเคสที่เป็นข้อค้นพบหลักของ RQ3 พอดี

## 11. ต้นทุนไม่ใช่ประเด็นที่ขนาดนี้

| scope | ρ | draft median | draft p95 | build | build เป็นกี่ step |
|---|---|---|---|---|---|
| request-local | 0.000060 | 1.23 µs | 1.66 µs | 0.1 ms | 1.19 |
| narrow(10) | 0.000073 | 1.50 µs | 1.68 µs | 4.6 ms | 1.15 |
| domain | 0.000072 | 1.49 µs | 1.63 µs | 58.9 ms | 14.73 |
| global | 0.000073 | 1.50 µs | 1.62 µs | 305.6 ms | 15.28 |

**ρ อยู่ที่ ~0.00007 ทุก scope** — การเปิด index เป็น O(1) ไม่ขึ้นกับขนาดคลัง drafter จึงแทบไม่มีต้นทุน

**ต้นทุนสร้าง index สูงสุดคิดเป็น 15.3 step ของ target model เทียบกับ S ทั้งหมด ~36,100 step = 0.04%**

**ข้อสรุป:** ที่ขนาดคลังระดับนี้และ target model ระดับ 7B **scoping ไม่ได้ซื้อ latency มันซื้อหน่วยความจำกับ acceptance** เส้น "รวม build" กับ "ไม่รวม build" ทับกันเกือบสนิท

เรื่อง amortization (R) จะมีน้ำหนักก็ต่อเมื่อ target model เร็วกว่านี้มาก หรือคลังใหญ่กว่านี้มาก

## 13. คำตอบของ RQ3

**ได้ — scoping ยกระดับ speculatability ได้จริง และแยกจากผลของขนาดคลังได้ด้วย control ที่ขนาดเท่ากันเป๊ะ**

**แต่กลไกไม่ใช่ "แคบแล้วดี" มันมีสองระบอบที่ไม่ต่อเนื่องกัน:**

**ระบอบที่ 1 — prompt** ข้อความของ request เองมีความหนาแน่นของข้อมูลสูงที่สุด 557 token ให้ score เท่าประวัติ 32,291 token และเป็นเพราะ **entropy ต่ำ** ไม่ใช่เพราะ support สูง

**ระบอบที่ 2 — ประวัติที่เก็บไว้** ในระบอบนี้ **กว้างกว่าดีกว่าเสมอ** จนถึงขอบเขต domain แล้วเริ่มถอย การเก็บประวัติแค่บางส่วนแย่กว่าไม่เก็บเลย (speedup 0.977 ต่ำกว่า 1.0)

**และมีขอบเขตชัดเจน: เก็บประวัติข้าม domain ทำให้แย่ลง** ทั้งที่ข้อมูลมากกว่า 5 เท่า เพราะ entropy สูงขึ้นเร็วกว่าที่ support จะชดเชย

### ข้อเสนอเชิงปฏิบัติ

```
✅ เก็บ prompt ไว้ในคลังเสมอ         ถูกที่สุด ได้ผลมากที่สุดต่อ token

❌ อย่าเก็บข้าม domain                จ่ายแรม 4.3 เท่า ได้ผลแย่ลง

```

## 14. ข้อจำกัด

### ⚠️ ข้อที่ 1 — target ประกอบจาก summary หลายเอกสาร (สำคัญที่สุด)

เพื่อให้ทุก domain มี target ยาว 200 token เท่ากัน เราต่อ summary ของเอกสารที่ต่อ ๆ กันจนครบ วัดจริง:

| domain | ความยาว summary | ต้องใช้กี่เอกสารเพื่อครบ 200 token |
|---|---|---|
| arXiv | 196 token | **1.0** ✅ |
| CNN | 53 token | 3.8 |
| XSum | 26 token | 7.7 |
| SAMSum | 23 token | 8.7 |

**สำหรับ XSum และ SAMSum ประมาณ 87% ของ target มาจากเอกสารที่ไม่ได้อยู่ในคลังเลย**

ข้อนี้**กดเพดานของทุก scope ลงพร้อมกัน** และอธิบายว่าทำไม arXiv ถึงโดดกว่าชาวบ้าน และทำไม request-local ถึงตกต่ำกว่า 1.0 ใน XSum/SAMSum

**arXiv คือ domain เดียวที่ผล request-local สะอาด**

**ทางแก้รอบหน้า:** ใช้ target ที่มาจากเอกสารตัวเองล้วน ความยาวต่างกันได้ตาม domain กำหนดขั้นต่ำแทน (เช่น ≥ 64 token)

### ⚠️ ข้อที่ 2 — ตัววัดไม่ไวพอที่คลังใหญ่

ที่คลัง 200k token score แยก treatment กับ control แทบไม่ออก (1.05× ภาพรวม, CNN 1.00×) ทั้งที่ speedup บอกว่าต่างกัน 1.027× — ดูหัวข้อ 10 ข้อ 2 และ 3

### ⚠️ ข้อที่ 3 — สืบทอดจาก RQ2 ทั้งหมด

`t_v(1) = 20 ms` และ `β = 0.01` เป็นค่าสมมติ · ρ เอาเวลา drafter บน CPU มาหารด้วย t_v ที่สมมติเป็น GPU · cost model ยังไม่เคย validate กับระบบจริง · ใช้ ground truth แทน output ของ target model ทำให้ L/S ที่รายงานน่าจะเป็นขอบล่าง

ทุกผลลัพธ์บันทึก `source = "assumed"` กำกับไว้ในไฟล์

### ⚠️ ข้อที่ 4 — กลุ่มคือ dataset ไม่ใช่ผู้ใช้

"domain" เป็นกลุ่มที่มีอยู่จริง แต่ไม่ใช่กลุ่มแบบ per-user หรือ per-session ที่ระบบให้บริการจริงเจอ ข้อสรุป "domain พอแล้ว" อาจไม่ย้ายไปยังกรณีที่กลุ่มแคบกว่าและเหนียวแน่นกว่า

### ⚠️ ข้อที่ 5 — ประวัติเป็นชุดคงที่

ประวัติเป็น seed corpus ที่มาก่อน request ทั้งหมด ไม่โตขึ้นระหว่างเสิร์ฟ ทำให้ scope key คงที่และ R วัดได้ตรง แต่แปลว่าไม่ได้วัดผลของ cache invalidation

### ⚠️ ข้อที่ 6 — เอกสารถูกตัดที่ 1,024 token

เพื่อไม่ให้เปเปอร์ arXiv ฉบับเดียว (ยาว ~6,000 token) กลบ narrow scope ทั้งก้อน แปลว่าคลังเห็นแค่ส่วนต้นของเปเปอร์

### ⚠️ ข้อที่ 7 — Wikipedia ไม่ตัดตามขอบบทความ

ประวัติของ Wikipedia เป็นช่วง 1,024 token ที่ตัดจากสตรีมโทเคน ไม่ได้ตัดตามขอบเขตบทความจริง

## 15. งานที่ควรทำต่อ

**ลำดับสูง**

1. **แก้การสร้าง target** (ข้อจำกัดที่ 1) — กระทบการตีความมากที่สุด
2. **ตรวจว่า "domain พอแล้ว" ยังจริงไหมเมื่อกลุ่มแคบกว่า** — SQuAD `title` เป็นกลุ่มของจริง (มัธยฐาน 169 คำถาม/หัวข้อ) ใช้วัด speculatability ได้ แม้วัด speedup ไม่ได้

**ลำดับกลาง**

3. **วัด β จริง** — forward pass ที่ B=1..8 บน Qwen2.5-0.5B ไม่กี่นาที เปลี่ยนจากค่าเดาเป็นค่าวัด
4. **validate cost model** — รัน end-to-end จริง 1 workload เทียบ measured vs modeled ให้ต่างไม่เกิน 20%
5. **prompt + domain รวมกัน** — การทดลองนี้เทียบ prompt *หรือ* ประวัติ ยังไม่ได้ลองรวม ซึ่งน่าจะเป็นทางเลือกที่ดีที่สุดในทางปฏิบัติ
6. **ปรับสูตร score ให้ไม่ลงโทษ coverage ต่ำ** — เช่น รายงาน coverage แยกจาก (1−entropy) แทนที่จะคูณกัน เพื่อไม่ให้พลาดเคส "เจอน้อยแต่แม่น"

**ลำดับต่ำ**

7. ประวัติแบบโตขึ้นเรื่อย ๆ + นโยบาย invalidate index
8. เพิ่ม domain ที่ห่างจากที่มีอยู่ (โค้ด, ภาษาอื่น)

## ภาคผนวก — ตัววัดทางเลือก

ระหว่างพัฒนาได้ลองตัวที่สาม **`oracle_accept_rate`** = สัดส่วนตำแหน่งที่ token ซึ่งพบบ่อยที่สุดในคลังตรงกับคำตอบจริง

ต่างจาก support/entropy ตรงที่ **มันเทียบกับคำตอบจริง ส่วนสองตัวนั้นบรรยายเฉพาะตัวคลัง**

| ตัววัด | correlation กับ speedup (รวม) | (ราย domain) | จัดอันดับตรงกับ speedup |
|---|---|---|---|
| score ของ RQ1 | +0.980 | +0.947 | ❌ สลับ 1 จุด |
| oracle_accept_rate | +0.974 | **+0.970** | ✅ ตรงทุกจุด |

ต่างกันเล็กน้อย แต่ oracle ไม่มีปัญหาเรื่องการลงโทษ coverage ต่ำ ตัวเลขเก็บไว้ในไฟล์ผลแล้วทั้งคู่ (`rq1_score`, `oracle_accept_rate`) เผื่อต้องการเทียบ

**ยังไม่ได้ตัดสินใจว่าจะใช้ตัวไหนในเปเปอร์ — รอคุยกับอาจารย์และ Santa (เจ้าของ RQ1)**
